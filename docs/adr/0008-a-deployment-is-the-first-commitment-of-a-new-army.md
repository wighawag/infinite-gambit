# A deployment is the first commitment of an army that does not exist yet

An army id is `nonce << 160 | owner` (the owner's `nonce`th army, nonce from 1), so every army id sits above any address-derived id and the client can name the army its next deployment will create before committing (`getNextArmy`). A deployment is then an ordinary `makeCommitment` for that not-yet-existing id: `_playerOf` lets it through only as the owner's NEXT army and only for the owner or their delegate, and the commit creates the army, moves the fixed stake from the account's reserve into the army's (which makes the army a waited-for member in the same cycle) and bonds it. It is revealed by the ordinary `reveal`, as ONE `Move` whose `from` and `to` are both the spawn point, so chess has one action type for deployments and moves alike. We chose this so that the commit-reveal base's client (the adapter, the chunked chain, the local revealer, fuzd, recovery, the stored submission keyed by identity) carries a deployment unchanged: the submission is keyed by the army from before the army exists and the identity does not change when it does. We rejected a separate `deploy`/`revealDeployment` route pair (a second adapter and a second action type in every stored record), an opaque counter id (the client could not key the submission before the commit lands), and a deployment struct distinct from `Move` (two encodings of what a submission holds). The cost is that the ARMY ID LAYOUT and the deployment's `Move` encoding are wires: changing either strands every deployment in flight, which freezes or burns the army.
