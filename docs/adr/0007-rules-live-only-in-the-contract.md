# The chess rules live only in the contract, and the client reads the board through a resolving view

Move legality, resolution and the bot's scoring all run the contract's own `pure` rule. The client reaches it through the template's simulation route (`$lib/game/simulation`), never through a TypeScript copy. The board is read through a contract view that resolves lazily across a viewport, not reconstructed by an indexer. We rejected a TypeScript copy held equal by shared tests because two implementations of simultaneous chess will drift, and when the client and the chain disagree it costs a player a move or an army. We rejected indexing the state because lazy resolution (`docs/adr/0002-order-free-lazy-resolution.md`) means the stored state is not the board: an indexer would have to redo the resolution, which is the same TypeScript copy by another route. An indexer may still come back for history (a replay of past cycles), never for current state. The cost is that every legal-move highlight is a sandboxed call rather than a function call, which the in-browser chain and the simulation worker exist to make cheap.
